## 2. タスクA：R0最狭時の残留開口を3D幾何から調べる【再計算0本】

### 2.1 何を検証するか

最も閉鎖に近いR0の `Amin_min ≈ 0.07563 mm²` が、(a) AP端に残る開口、(b) AP中央・局所に残る開口、(c) x断面選択／幾何積分と接触判定の不整合、(d) 実際に狭いが閉鎖閾値だけに未到達、のどれに近いか判定する。**既存計算の物理式は触らない。**

### 2.2 入力をまず探索

- R0固有の `run_dir`, `manifest`, `params`, 使用モードVTU/周波数/NAS、`area.dat`, `section_x.dat`, `glottal_methods.csv`, 接触診断、各ステップの `modal_native.bin`／変位履歴、可能なら変形VTU。
- 前回 `writeDeformationVtu=0` が使われた可能性が高いので、**VTUが存在すると決めつけない**。20モードすべての一般化座標 `q_n` が取得可能なら元の座標・モード形状と `u=Σφ_m q_m×1e3 [mm]` で代表時刻の左右形状を再構成する。右声帯の鏡映・初期gap補正・モードの並び／正規化を当該実装と一致させる。qと更新後VTUの1ステップずれに注意。
- R0の `modal_native.bin` は、前回レポート記載の最終区間 **n=19999を仕事検証から除外**した形式かメタデータで確認。除外を勝手に解除しない。
- 全20モード座標がなく、変形VTUもなく、幾何の再構成が不可能なら **UNDETERMINED_INPUT_MISSING** として停止。少数選択モードからの近似を「R0の正確なギャップ」と扱わない。

### 2.3 実装

`tools/kanaya_ablation/analyze_r0_residual_aperture.py`（既存ディレクトリに合わせてよい）として後処理を追加し、**現行の `ChannelSections` と同じ**断面位置、交線の選択、AP方向の有効区間、負ギャップ切り捨てを再現する。現行C++の対象実装・関数と参照コミットをレポートに記す。

1. `area.dat` 等から全時刻のAminを調べ、0.10–0.20 sの**複数の局所極小（異なる周期）**を抽出する。全評価窓の最小時刻と、ほかの周期の少なくとも4イベント（あれば）を選ぶ。出力ステップの丸めや欠損があれば明記。
2. 各イベントの最狭物理x平面で、同一物理z座標上の `y_L(z),y_R(z),h_signed(z)=gapSign*(yR−yL)`、`h_positive=max(h_signed,0)`、共通AP被覆区間、接触/侵入に相当する**負ギャップ領域**を求める。zに穴がある場合に線形補間で架空の表面をつながない。
3. 同じx平面について `A_replay=∫max(h_signed,0)dz` と `A_solver` を照合し、先に一致判定。丸め前の保存値があればそれを優先。**この検証に失敗したイベントについては開口分布の物理解釈を保留**。
4. 0–17 mmのAP方向を一律積分しない。採用した有効z区間を明示し、部位を左右端（基準AP長の先端側・後端側各1 mm、感度検証で0.5 mmと2 mmも採用）、中央に分ける。各部位の**開口面積への寄与 mm² / 全面積%**、開放z幅、最大・平均正ギャップ、負ギャップ幅を報告する。zの原点とAP前後の対応を入力メッシュから確認し、勝手に解剖学的「前／後」を付けない。
5. `Amin`を作る断面だけでなく、隣接±2断面と接触近傍も比較し、**最狭部xの動き**とAP残留開口を区別する。
6. **接触反復の `contactFlag`／採用ペア区間比／最大侵入**は接触アルゴリズムが予測した `t_(n+1)` の値であり、更新前の断面形状 `t_n` と必ずしも同時刻・同じ面定義ではない。可能なら既存の接触ペア詳細・時間IDと照合。なければ「負ギャップ」と「採用接触ペア」を別指標にして、同一とは書かない。負ギャップがあるから全声門閉鎖、とも判定しない。
7. **接触しながら開口が残る**ことは幾何上あり得る。0.01、0.05、0.1 mm²の**代替閾値の下での時間率**を補助で求めるが、公式の閉鎖閾値は0.01 mm²のまま維持し、閾値変更で「周期閉鎖達成」と認定しない。代表周期でどの程度閾値に近づくかも報告。
8. 可能なら**実際の内側表面を固定物理xで2Dマップ**（x対zのsigned gap、無効はNaN）にして、AP端だけか中央にも残るか見えるようにする。行ごとに不規則なxを縦方向で単に接続しない。

## 3. タスクB：S3を1本だけ実行 ― S2を基準に旧上流音響回路を復元

### 3.1 固定条件・唯一の変更箇所

**必ずS2の実行に使った `params.txt` とmanifestを複製**し、実効値からの差分を検査する。`input/param.txt` の初期例示値から新しく作り直さない。

### 3.2 実装方針

- 既存 `src/fluid/flowModel.cpp` とパラメータ読込みの最小変更で、**名前付き任意設定** `upstreamAcousticProfile = modern | legacy_main`（名前は既存仕様と衝突しなければこの案を使う）を追加。既定 `modern`。legacyにしたときのみ上表の4つの上流値とLu定義を旧C++ mainから適用する。S2とS3の比較に関係しない `Rk,Rv,Lg` 等はそのまま。既存の `vocalTractLengthM` と `glottalMethodProfile` はそのまま使用。
- `Lu` は局所変数名だけ見て変更しない。**声門下流量更新式の `Lu`, `2Lu`, `Lui+Lu`, `Lg1+La+Lu` の各使用箇所**を旧C++ mainと行単位で照合し、一貫性を確認する。旧mainと一致しない場合は式の違いを列挙した上で、**ユーザー指定の旧回路相当の数式に合わせる**。旧条件を名乗りながら混在させない。
- `A_inlet=πr_inlet²`, `A_sub=πr_sub²`, `Δx_sub=L_sub/N_sub`、`Lui,Cui,Lu,Cu,R2` など**従属係数をすべて再計算**。旧C++参照がこれ以外の変数（境界状態・番号・圧力更新順等）を使うなら、旧式と今回の等価性の範囲を明示する。`R2` の断面積／係数も確認。
- C++の現在の声門下 `Pu,Uu` 配列は `N_sub` に依存するので、`3`分割へ変更した状態でindex範囲・境界位置・初期値・最後のNRへの圧力項をテスト。3/10セクションで配列外アクセスしない。`N_vt=10`と声道0.175 mも実効一致を確認。
- 既存 `params` に直値を設定できるなら重複実装しないが、他ケースの既定値に影響させない。参照旧mainのコミット、変更コード位置、生成された `Lui,Cui,Lu,Cu,R2,La,Ca,Lr,Rr` と寸法を `manifest` と小CSVにすべて記録。
- **旧流体方式一式であっても旧成功モデル全体の完全再現ではない**。現在の左右独立接触、接触参照40 Hz、未確認の旧実効モード数・質量条件などは残ることをレポートで明示。

### 3.3 本番前の必須検証（短く）

1. `icpx` Releaseビルド。前回の単体テスト群／最低限の現行回帰を実施。**S2実効設定＋新オプション省略の短いスモーク**で旧S2と既知の物理計算出力が一致すること（初期非線形接触が絡む場合、スレッド同一条件でbitwise照合。不可なら誤差根拠を明示）。既存S2の20,000 stepを再計算しない。
2. 旧main参照式に基づく上流係数の単体テスト（r_inlet=0.15,L_inlet=0.5,L_sub=0.25,N_sub=3,Lu=ρΔx/A）。**ループの `2Lu` を誤って別定義へ変えない**。3/10分割の正常終了と有限値を確認。
3. 旧S2の `L_vt=0.175` を維持し、下流Pdの初期化・更新順・NR残差、左右対称性を短いステップで確認。S2比較用の既存チェックを流用する。
4. 不正プロファイルを拒否。`legacy_main` が適用されていないままS3とラベル付けする事故を、manifestの係数値アサーションで防止。

## 4. タスクC：S2 vs S3を同じ定義で比較

各ケースの `run_metadata.json`／`params`／出力列名を確認し、前回の解析ツールをできる限り再利用する。評価期間は前回と同じ0.10–0.19998 s、振幅比較は `n=10000..14998` と `n=15000..19998` 各4999区間。モード仕事最終n=19999の除外規約を守る。時間と定義が違うデータをつなぎ合わせない。

**表に載せる必須指標**：

- `Amin`：平均、AC RMS、各局所極小、最小、閉鎖閾値`≤0.01 mm²`に対するclosed fraction、連続閉鎖区間/周期性。閉鎖がなければCQ・閉鎖由来f0は**NaN**。
- 左右の固定**材料点** uy：平均、AC RMS、後半/前半比。節点の固定物理参照座標`(x,z)≈(9.2,8.5) mm`をS2と同一に。左右鏡映残差。
- 声門流量 Ug：平均・AC RMS・スペクトルピーク、圧力ランプ終了後の振幅時間変化。FFTピークを閉鎖由来f0と呼ばない。
- `Pg`、上流／下流回路圧力、`Uu`, `Pu`、実効 `Lui,Cu,L_u` 等、NR各項と収束残差。
- 接触：採用ペアのあるステップ割合、最大侵入、接触圧／局所力の代表値。**接触ペア≠全閉鎖**。
- 流体力：正負圧別の開大合力、作用面積、主モード1/4/5/7の Q と仕事（全20モード合計も）。`W=ΣQ_nΔq_n`, `Wmean`, `Wfluct`, `Wpos`, `Wneg`, damping参考。モード質量Gramの非対角とNewmark数値散逸の限界に注意。単位はmJなど明記。
- もしS3で閉鎖すれば、それは**S2→S3の上流回路ブロック変更が閉鎖へ寄与した**という結果であり、旧成功コード全体の再現や因子ごとの因果確定ではない。逆に閉鎖しなくても上流回路の影響ゼロとは書かない。

**数値検証ゲート**：全データ有限（適法NaNの定義を分離）、左右対称、NR残差、一般化力Qの左右整合性、`Wtotal=Wmean+Wfluct`, `Wfluid=Wpos+Wneg`、保存済みwindow合計との一致、S2既存結果の不変、実効パラメータ差分が「上流回路ブロックのみ」であること。前回の閾値／validation formatを再利用。

## 5. CPU使用と最短時間化：前回の実測結果を優先

前回の測定（WSL2、CPU可視0–15、8 core×2 SMT、i5-14400F、2000-step比較、VTUなし、診断あり）：

| modern単独 4thread | 49.20 s |
| modern単独 8thread | **47.17 s** |
| modern単独 16thread | 51.32 s（むしろ悪化） |
| 2ケース同時 4thread×2job | **58.25 s / 2ケース** |
| 2ケース同時 8thread×2job | 58.51 s / 2ケース |

- **今回は本番S3が1ケースだけ**なので、初期方針は**8 OpenMP threadsで単独**実行。2つの20,000-step連成計算を意味なく同時実行しない。R0の後処理は本番S3と重ねてもよいが、CPUバウンドならプロセスを別物理コアへpinし、S3のスループットが悪化しないよう配分する。最短が不明なら後処理は本番前後に実施。
- 実機の cpuset、P/E/SMT と空きリソースは `lscpu -e=CPU,CORE,SOCKET,ONLINE`, `taskset -pc $$`, `nproc`, `cat /sys/fs/cgroup/cpu.max`, `free -h` 等で確認。**報告書のCPU IDを無条件に流用しない**。単独8threadのpinは互いに異なる物理コアを優先して割り当て、Intel P/E混在の現実のコア情報に応じて調整。
- 実行環境例（実際のエントリポイントは既存 `tools/kanaya_ablation/README.md` を優先）：

```bash
export OMP_NUM_THREADS=8
export OMP_PROC_BIND=close
export OMP_PLACES=cores
export MKL_NUM_THREADS=1
export OPENBLAS_NUM_THREADS=1
export BLIS_NUM_THREADS=1
# 必要に応じて確認済みの物理コア集合へtaskset -c ...
# /usr/bin/time -v <既存のランナーでS3だけ起動> > S3_run.log 2>&1
```

- 全CPUを使うことは**最大論理スレッド数の使用**と同義ではない。前回の8スレッドが単独最速だったため、16スレッド固定や多重ジョブによる過負荷は避ける。
- まず既存の実測を採用し、**広範囲の2000step CPUベンチを繰り返さない**。環境に変化が明らかな場合のみ100–300step程度の同一条件スモークで4/8threadを1回ずつ比較。ただし起動・モデル読込の定数時間が大きく、非常に短いスモークから本番速度を断定しない。前回の壁時計・loop時間を併記。
- テストと独立解析のPython/BLASがS3計算スレッドに過剰に重ならないよう制御。スレッド安全・OpenMPの決定性を確認し、数値結果の変化を速度最適化のために許容しない。
- `writeDeformationVtu=0` は前回数値不変を確認済み。**R0の空間解析に必要な既存情報を削除せず**、S3のVTU抑制は維持。追加ログは小さく、CSVの大量同期flushはしない。
- コンパイルは `cmake --build ... -j <使用可能コア数>` 程度で高速化可。ただしRAM/負荷と競合を観察。物理計算のOpenMPスレッド数とは分けて設定。計算時間・起動時間・ピークRSS・コア割当を記録する。
